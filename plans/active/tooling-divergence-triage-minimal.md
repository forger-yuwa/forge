## 1. 目的

発散した run を前にして時間が溶けるのは、**証拠を毎回手で集め直している**からである。
既存の決定論ゲート ([`check_convergence.py`](../../solver_density_cuda/tools/check_convergence.py) ほか) は
**状態** (PASS / NOT CONVERGED / DIVERGED) を出すが、**証拠** (最初に非有限になった step と列、実効設定と既定の差、
IC の出自) は毎回手で集めている。

本計画は「その手集めが何分かかっているか」を先に測り、**測った分だけ**自動化する。

外部判断モデル (Jev。§3.2) の導入は本計画の目的ではない。**規則で決まらない残余が実在すると測れたときに、
別 plan で改めて検討する**ための材料を作ることまでがスコープである。

## 2. スコープ

- **やる**
  - **Step 0 (コードを書く前)**: 直近の発散 10 エピソードを手で調査し、**何にどれだけ時間がかかったか**を記録する。
  - Step 0 の記録で上位に来た作業だけを `diagnose_run.py` に実装する。初期実装の上限は次の 4 つ:
    1. 既存 checker の結果への参照 (再実装しない)
    2. **全 phase を走査した最初の「観測された」非有限値** (step 規約・phase・inner・列を明示)
    3. 指定された異常ダンプ内の非有限 DOF の index・座標・件数 (**領域分類はしない**)
    4. Step 0 で実際に効いた**少数の規則**だけ (根拠リンク付き)
- **やらない** (codex 2 巡目で「価値計測前の投資」と判定されたもの)
  - 全設定の実効値復元、過去 run の provenance 復元、全 `res_*.h5` の全量走査
  - 境界所属による領域分類 (入口 / 壁 / 軸 / seam)、`check_mesh_quality.py` の拡張
  - 原因仮説カタログ、原因名の当てっこ
  - **Jev クライアント・キャッシュ・フック連携・外部送信** (本計画では一切実装しない)
- **恒久的な非目標** (Jev の採否に関わらず)
  - フック (`hook_*.py`) / `run_case.sh` / 設計ループ ([`evaluate/runner.py`](../../design/forge_design/evaluate/runner.py) は
    共通ラッパーを同期呼びする) への**外部 API の同期呼び出し**。診断は常に明示実行の CLI。
  - 外部モデル出力を [`AGENTS.md`](../../AGENTS.md) の VERDICT の代替にすること。
    `divergence-and-startup.md` のチェックリストを省略すること。

### 3.2 Jev の事実 (判断材料として記録。本計画では使わない)

TypeSafe AI の「System One モデル」。文章を生成せず、型付き質問 (`noul` / `choice` / `score`) に
確率 + `confidence` で答える。

- **公開 4 日** (早期アクセス 2026-09-15、1.13 が 09-18)。`jev-latest` は**可変タグ**。
- 価格 $0.042/MTok・出力無料、70–500 ms、context 32k。ただし**補助金付きの可能性を公式が明記**。
- 公式 SDK `typesafe_sdk` / `TYPESAFE_API_KEY` / `RetryPolicy`。
- 較正 (RLCD) は**集団に対して**成り立つ性質で、個々の答えの正しさは保証しない。**理由を返さない**。
- 弱点 (1.13 jaggedness): 数え上げ・数値精度・日付比較、間接推論、無関係文脈に引きずられる、
  `P(true)+P(false)=1` を仮定不可。
- **CJK は精度が落ちると公式が明記** → 日本語の本リポジトリの文面をそのまま state/criteria にできない。
- 公式の作法: 複雑な判断は**原子的な質問に分解**し合成はコード側、state は prose でなく名前付き JSON、
  しきい値は自前データの confidence–accuracy 曲線で決める。

成熟度 (公開 4 日・可変タグ・補助金価格) と CJK 精度低下は、**いま構造を載せない**根拠として §6.3 に効かせる。

## 4. 設計方針

### 4.1 順序

**測る → 測った分だけ作る → 残余を測る → (別 plan で) モデルを検討する**。
草案 v1 は最後から、v2 は真ん中から着手していた。本稿は先頭から始める。

### 4.2 Step 0: 手作業の実測 (コードより先)

直近の発散 10 エピソード (**run ではなく調査エピソード単位**。同一根本原因の CFL 掃引・restart 派生は 1 件) について、
解決までを手で追い、次を記録する。

| 記録項目 | 注意 |
| --- | --- |
| 作業ごとの所要時間 | **人間の実作業時間と計算待ちを分ける**。未解決・打ち切りも記録する |
| 参照したファイル・コマンド | どの証拠を何回集め直したか (自動化の候補はここから決まる) |
| 投入した切り分け run | 本数と計算費用を記録。「不要だった」は**事前に決めた基準**で別途判定する |
| 決め手になった証拠 | これが `diagnose_run.py` の実装対象 |

**この 10 件の記録が本計画の第一の成果物**であり、実装範囲はここで決まる (先に決めない)。

### 4.3 `diagnose_run.py` の最小契約

出力は型付き JSON + 1 画面サマリ。各項目は `value` / `evidence` (ファイル:行 or 列名) /
`status` (`observed` / `unknown(理由)` / `not_applicable`) / `provenance` (`runtime_recorded` /
`read_from_current_file` / `derived_from_version`) を持つ。

- `checkers`: 既存 checker の VERDICT と**版・引数** (`--drop` / `--tail` / `--from-floor` 等)。再実装しない。
- `first_observed_nonfinite`: CSV 側と場側を**別々に**保持。各々に file / step 規約 / phase / inner /
  列 or 変数 / 観測間隔を付ける。**記録破損と solver 由来の非有限値を区別**する。
- `nonfinite_dofs`: 指定された異常ダンプ内の非有限 DOF の index・座標・件数のみ。**領域分類はしない**
  (境界所属は結果 h5 単体で完結せず、入口∩壁のような重複所属も実在する →
  [`boundary-node-inlet-corner-wall.md`](boundary-node-inlet-corner-wall.md))。
- 既定は軽量経路 (CSV・`forge_run.log`・指定ダンプ)。全履歴走査は `--scan-all`。
  **走査した範囲と未走査範囲を必ず出力する**。診断 CLI 自身の所要時間も出力する。

### 4.4 規則の形

Step 0 で実際に効いた規則だけを実装する。出力は 3 層に分け、**原因を 1 つ当てる形にしない**
(原因・症状・場所は別物で、EOS 床 NaN のように「反復不安定の終端症状」が複数分類に入りうる →
[`time_integration-update-positivity-guard.md`](../accepted/time_integration-update-positivity-guard.md))。

1. `observations` — 機械的に導ける事実
2. `checks` — 次に確認すべき項目。**必ず手順書の節や plan へのリンクを持つ**
3. `hypotheses` — 原因仮説。複数可・`unknown` 可・`insufficient_evidence` 可。**確定ではないと明示**

規則ごとに「必要な入力事実」を先に定義する。必要事実が証拠束に無い規則は**実装しない**
(草案 v2 は手順書を「1 対 1 で写す」としながら、BC 値・IC の流速/圧力/乱流量を束に持っていなかった)。

### 4.5 効果の測り方

**「規則が何かを出した率」と「調査負担が減ったか」を別指標にする**。前者だけなら、汎用チェックを 1 つ出し続ければ
いくらでも良く見えるため、採否には使わない。

| 指標 | 定義 |
| --- | --- |
| 出力率 (参考) | `checks` が非空だった割合。**採否に使わない** |
| 次の確認の有用性 | 独立採点: 提示された `checks` 最上位が有用だったか。**陰性結果 (疑いを潰した) も有用に数える** |
| 危険な提案 | 誤った設定変更や無駄な長時間 run を誘発しうる提案の件数。**これは上限を置く** |
| 証拠不足の申告 | `insufficient_evidence` を正しく出せたか (黙って推測しないこと) |
| 調査時間 | Step 0 と同じ取り方 (実作業/計算待ちを分離、未解決も残す) |
| 診断コスト | CLI 自身の実行時間と I/O |

## 5. 実装ステップ

1. **Step 0 の 10 エピソード実測** (§4.2)。コードは書かない。
2. 実測で上位に来た証拠だけを `solver_density_cuda/tools/diagnose_run.py` に実装 (§4.3)。
   全 phase 走査は `passive_gate_common.py:311` / `plot_implicit_residuals.py:17` を参考に
   **薄い共通読み出しを抽出**する (新しい収束判定器は作らない)。
3. Step 0 で効いた規則だけを §4.4 の形で実装。
4. 固定データでの否定側テスト (§6.1)。
5. 次の 10 エピソードで §4.5 を測る。**ここで「規則で足りる」なら本計画は完了 (最良の結末)**。
6. 残余が実在する場合のみ、Jev spike の可否を §6.3 の 1 点だけで判断し、**別 plan を起票**する。

## 6. 検証

### 6.1 `diagnose_run.py` の検証 (肯定側と否定側の両方)

- **肯定側**: 取得可能な入力に対しては**期待値を必須**とする (「`unknown` でも合格」にしない)。
  `unknown` が許されるのは**欠測時に理由付きで返した場合だけ**。
- **否定側 (固定の小データ)**: 正常な node 壁の距離ゼロ、内反復だけの異常、壊れた CSV (記録破損 vs 非有限値)、
  対象外 run (収束途中の NOT CONVERGED)、結果とメッシュの不一致、`res_*.h5` 無し、途中終了。
  **誤警報を出さないこと**を明示的に確認する。
- 規則の採点は**複数の妥当な確認項目を許す** (原因名の一致で採点しない)。

### 6.2 効果の検証

次の 10 エピソード (Step 0 とは別) で §4.5 を測る。**エピソード単位**で数え、未知・複合原因・情報不足も残す。
判定は「調査時間の短縮」と「危険な提案の件数」の 2 つで見る。出力率は参考値。

### 6.3 Jev に進むかの判断 (本計画で決めるのはこの 1 点だけ)

**採否の試験は本計画では行わない** (codex 2 巡目: 開発用 30 件の shadow では人間の調査時間も誤変更も測れない)。
本計画で決めるのは「**別 plan を起票して spike に進むか**」だけであり、条件は次の 2 つ。

1. §6.2 の残余に、**意味解釈が要る**種類の負担が残っている (数値・条件で決まるなら規則を足す方が安い)。
2. その負担が、測定された時間として**保守費を上回る規模**である。

**効果が未確認であることと、効果が無いことを区別する。** 測れなかった場合は「保留 (実装しない)」であり、
「Jev 不採用の実証」ではない。

進む場合、別 plan 側で**先に**固定すべき事項 (本計画からの申し送り):

- 主指標を 1 つ事前指定し、最小実用改善幅と誤誘導の上限を置く。事後に有利な指標を選ばない。
- 比較対象は「規則 + 根拠リンク + 必要時に既存エージェント (根拠ファイルを追加で読める)」。1 回投げ同士の比較にしない。
- 事例は**調査エピソード単位**、ラベルは**訂正後の結論**を使い (過去に「真因」が覆った例:
  [`architecture-axisym-axis-singularity.md`](../accepted/architecture-axisym-axis-singularity.md))、
  当時の入力を復元できない事例は「不確実」として区別する (config 3,491 本の移送履歴:
  [`config-key-pruning.md`](../accepted/config-key-pruning.md))。**開発用 / 較正用 / 最終評価用を分離**し、
  最終評価は将来側の期間から取る。
- 外部送信は**証拠束をそのまま渡さない**。許可リストで**別の送信オブジェクト**を生成し、その正確な内容に opt-in を取る
  (証拠束にはパス・元 run・commit・座標・設定値が入る)。認証ヘッダはログに残さない。
  提供者側の保存 / 学習利用条件を確認する。
- **実モデル版を確認できない期間の結果を同一評価に混ぜない** (`jev-latest` は可変タグ)。
  通信失敗はモデルの棄権と別状態にする。
- state と質問は**英語**で書く (CJK 精度低下)。質問は原子的に分解し合成はコード側。ただし
  「候補 X を最優先すべきか」は**候補集合を誰が作るか**を先に決めること (真偽型にしただけでは原子的にならない)。
