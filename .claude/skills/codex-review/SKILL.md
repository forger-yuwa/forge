# /codex-review — codex に外部レビューを頼む

ルールの正本は **AGENTS.md「codex レビュー」**、手順の正本は
**[`procedures/codex-review.md`](../../../procedures/codex-review.md)**。本 skill はそこに書かれていない
**プロンプトの作法と失敗パターン**だけを足す。重複は書かない。

## 1. まず: plan 段/result 段ならツールを使う

```bash
python3 solver_density_cuda/tools/codex_review.py plans/active/<plan>.md --stage plan    # 実装着手前
python3 solver_density_cuda/tools/codex_review.py plans/active/<plan>.md --stage result --base main
```

起動作法 (read-only / stdin=/dev/null / stdout をパイプに通さない / reasoning=high) はツールが守る。
**自由形式の切り分け依頼**だけ手で `codex exec` を打つ。そのときも同じ作法を守る:

```bash
nohup codex exec --sandbox read-only --skip-git-repo-check "$(cat <prompt>.txt)" \
  < /dev/null > <scratchpad>/codex_<topic>.log 2>&1 &
```

- `run_in_background` で呼び、**timeout 1200 s 以上**。所要 5〜15 分。
- 進捗はログのサイズで見る。フリーズ疑いでも kill 前に `ps -o pid,etime,time` の CPU 時間を見る。

## 2. 禁止事項 (プロンプトに毎回そのまま書く)

codex は**コンテキストを自分で使い切る**。巨大ファイルを 1 つ読ませると、そこで打ち切られて
何も返ってこない。実際にこれで 1 セッション中に複数回失敗した。プロンプトに必ず書くこと:

```
## 禁止事項 (厳守)
- ファイルを変更しない (read-only サンドボックスで動いている)。
- **`*.log`, `residual_history.csv`, `res_*.h5`, `*.vtu`, `plans/README.md` を読まない** (巨大)。
- 下に列挙した `sed -n 'A,Bp' <file>` 以外のファイル読みをしない。grep は可。
- 両論併記で逃げず、**推奨は 1 つに絞る**。根拠は `ファイル:行` か提示した数値で示す。
```

そのうえで **「読んでよいもの」を `sed -n 'A,Bp' <file>` の形で列挙する**。行範囲を自分で調べてから渡す。
1000 行超のヘッダを丸ごと渡さない (`solverConfig.hpp` は該当する数十行だけ)。

## 3. プロンプトに必ず入れる 4 点

1. **指標の定義**: 何をどう測った数字なのか (切り出し範囲・トレンド除去・符号の意味)。
   定義が無いと codex は数字の大小だけで議論し、指標自体の欠陥を見落とす
   (例: `odd-even` 指標の応答が $\sin^2(\theta/2)$ で 2 節点に固有でない、という反証は定義を渡して初めて出た)。
2. **既に潰した候補の一覧**: これが無いと、もう棄却した仮説を推奨してくる。
   「何を変えて、指標がいくつからいくつになったか」を 1 行ずつ書く。
3. **今回の A/B の生データ**: run 名・設定差分・層ごとの数値を表で。**空振りだったことも隠さず書く**。
4. **問いを 1 つに絞る**: 「仮説を 1 つに絞って挙げ、それを切り分ける A/B を 1 つだけ設計してほしい
   (変えるのは 1 箇所、判定は上の指標)」。検討してほしい候補は (a)(b)(c) と挙げてよいが
   「これに縛られなくてよい」と添える。

## 4. 出力の読み方 (失敗しやすい)

- **最終回答は `tokens used` の**後ろ**に出る**。途中で `tail` して「打ち切られた」と誤判定しない。
  `awk '/tokens used/{f=1} f' <log>` で本文だけ取る。
- codex は**自分の前回の予測を撤回することがある**。撤回は価値のある情報なので記録に残す。
- codex が「今回の読み取り範囲では確認不能」と言ったものは、**確認できなかっただけで否定ではない**。
  必要なら読ませる範囲を足して再照会する。
- 指摘を鵜呑みにしない。根拠 (`ファイル:行` / run の数値) が無い、または根拠が実際と違う指摘は
  **再検証してから採否を決め、その結果も記録に書く** (誤指摘も記録として価値がある)。
- **コードを引用する前に、その case が実際に通る経路か確かめる。** 行番号を渡すと codex はそこだけ読む。
  実例: block-DPLUR (`blockDPLUR: 1`) の case なのに**スカラー経路**の行を渡してしまい、
  「指定の `inv_diag` は block-DPLUR のものではありません」と最初に訂正された
  ([`notes/reviews/2026-09-21-codex-c3x-implicit-energy-diag.md`](../../../notes/reviews/2026-09-21-codex-c3x-implicit-energy-diag.md))。
  同じ構造が別経路にもあったので結論は生き残ったが、**前提が外れていれば回答ごと無駄になる**。
  `grep -n` で**呼び出し側** (どのカーネルが launch されるか) まで辿ってから行範囲を決める。
- **「物理的に正しい係数はこれだから、実装は N % 過小」という論法は根拠を確かめてから出す。**
  実例: エネルギー行の陰解法対角を $\alpha/\nu$ で 11-39 % 過小と主張したが、
  $\alpha=k/(\rho c_p)$ は保存変数 `roe` の Jacobian 対角ではない ($k\,\partial T/\partial(\rho E)=\gamma\alpha$、
  さらに交差微分) と指摘され撤回した。**比率の議論は Jacobian を実際に書き下してから**。
- **codex が判定期間・判定方法について警告したら、それを「その依頼で渡した前提データ」にも遡って適用する。**
  実例: codex の「4000 step 後の差だけでは判定できない」を新しい A/B にだけ適用し、
  同じ依頼で「空振りだった」と渡した前回の A/B (これも 4000 step) には適用しなかった。
  16000 step で測り直したら空振りではなく **−27 %** 効いていた
  ([`notes/reviews/2026-09-20-codex-c3x-psiT-negative.md`](../../../notes/reviews/2026-09-20-codex-c3x-psiT-negative.md))。

## 5. 記録 (痕跡が残る形にする)

- 本文を `notes/reviews/<日付>-codex-<topic>.md`、生ログを同名 `.log` (git 追跡外) に置く。
  本文には「依頼内容」「結論 (原文要約)」「**当方の採否**」の 3 節を必ず持たせる。
- plan の **§6.1 レビュー記録**の表に 1 行 (段階 / 日付 / 記録 / 判定・指摘数 / 対応)。
  Critical / Major は §5.1 残作業表に入れるか、却下理由を §6.1 に書くかのどちらかにする。
- **回した/反映した応答には、記録ファイルのパスと採否を書く** (run パス明示・VERDICT 貼付と同じ扱い)。
- **別セッションが同じツリーで並行作業しているときは、相手の plan にレビュー行を書き込まない。**

## 6. 推奨をそのまま実装しないでよい場合

codex の A/B 案が**間接プローブ**で、こちらにより直接的な試験があるなら、直接的な方を先にやる。
その判断も記録の採否欄に理由つきで書く
(例: 「float32 の丸めが停止位置を決める」に対し、codex 案は「エネルギー更新だけ 0.5 倍」だったが、
`flowFormat.hpp` を `double` に切り替えた**全体 double ビルド**で一撃で棄却/支持できるのでそちらを先に回した)。
