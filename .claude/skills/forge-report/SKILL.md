# /forge-report — 計算結果を報告にまとめる

目的: 読者が**数字を信じてよいかを自分で判断できる**報告を作る。必要なのは綺麗な図ではなく、
(1) 何をどう解いたか、(2) 判定ツールが何と言ったか、(3) どの run のどのファイルか、の 3 つが
**数値結果より先に**出ていることである。

判定の方法・状態別の書き方 (段階起動の区間、`OSCILLATING` の平均±振幅、単調な `STEADY` の
漸近値、判定不能の扱い) は **AGENTS.md の該当節が正本**。ここでは重複させず、**報告物の構成**だけを決める。

## 0. 出力先

ユーザーの指定を優先する。指定が無ければローカル HTML を作り、`Artifact` ツールが使えるなら
それで公開する。恒久記録は別で、**`case/<case>/README.md` の「## 計算 run 一覧」表**が正本
(AGENTS.md)。設計判断・検証の結論は対応する `plans/*/<plan>.md`。
報告ページは**スナップショット**なので、末尾に「run 索引は README が正本、本ページは YYYY-MM-DD 時点」と書く。

## 1. 条件節は「数値結果より前」

**「最初の図より前」では足りない** (良い数字だけ先に出す報告がそれで通ってしまう)。守るのは:

> **条件節より前に置いてよいのは、報告の目的と対象だけ。**
> 数値結果・比較・「収束した」「一致した」の主張は、すべて条件節の**後**に置く。

HTML なら条件節を `section#analysis-conditions`、結果を `section#results` に分け、この順に置く
(DOM 順は機械的に確認できる)。条件節を折り畳み・非表示にしない。

冒頭に結論を 1 段落置くこと自体は良い。ただし**同じ段落の中で最大の限界も述べる**
(合わない領域・未収束・FAIL したゲートのうち最も重いもの)。書けないなら結論を冒頭に置かない。

条件節の中身は次の 4 点セット。

### (a) 解析領域の図

文章で「2D 周期 1 ピッチ」と書くだけにしない。**図にする。** 最低限:

- メッシュを薄いグレーで下敷きにする (解像度が伝わる)
- **境界パッチを `physID` ごとに色分けし、凡例に条件の種類を書く** (例: `inlet (physID 1) Pt, Tt, 軸方向`)
- 主流方向の矢印、座標軸のラベルと単位
- 対象物が領域に対して小さければ**拡大インセット**。**「拡大」と書いた枠は実際に拡大されていること**
  (全体と同じ範囲を貼っただけの枠を作った事故がある)
- **凡例・注記は空き領域か図の外に置く。** データに重ねない (両パネル共通なら `fig.legend` で図の下)

データは**その run の `mesh.h5`** から引く (`MESH/COORD` と `BCONDS/<physID>/vizBfaceNodes`)。
幾何ファイルや記憶から描かない — 図は実際に計算した領域でなければ意味がない。

### (b) 境界条件の表

**報告対象の段の実行時入力**から転記する (記憶や前段の config からではない)。
列は `physID / 境界名 / 課した条件 (kind) / 値・単位 / 分布の参照先`。領域図の色と対応させる。
壁温のような分布は「実測分布 (`wall_profile_5.csv`)」「一様 566 K」など**何を課したか**を書き、
**分布そのものもグラフにする** (課した境界条件は結果と同じだけ読者が確かめたい情報)。
実行時入力を確認できなければ「未確認」と明記する。

### (c) 数値設定の表

離散化 (node/cell・次数・リミッタ)、対流スキーム、時間積分 (定常/非定常・陰解法・CFL・
非定常なら時間刻み)、乱流モデルと壁処理、気体モデル、**次元と軸対称/周期の別**、
**初期値または restart 元**、節点数・壁節点数・第一セル厚。

### (d) ゲート

**合格したものだけを書かない。** FAIL・未実行・判定不能こそ条件節に要る。各ゲートについて:

| 書く欄 | 中身 |
| --- | --- |
| 対象 | run パス、対象量 / 壁群 |
| 区間 | どの区間で判定したか (段階起動なら `--segment` が連結した区間。段名で決めない) |
| コマンド | 閾値を含む実行コマンド |
| 出力 | VERDICT の原文 |
| 制約 | **その判定が結論をどこまで制約するか** 1 行 |

対象ツールは `check_convergence.py` / `check_quasisteady.py` / `check_wall_resolution.py` /
`check_mesh_quality.py`。**メッシュ品質は新造したときだけでなく使用メッシュについて常に**書く
(閾値と緩和の有無も)。壁解像は**壁群ごと**に、平均・超過面積割合・**超過位置**を書く。

- **FAIL があるまま結果を出してよい。** ただし制約欄を必ず埋める。
- **未実行・判定不能・適用不能を合格扱いしない。** 表から消さず、その文字列のまま書いて理由を添える。
- **未収束の「物理的原因」を条件節で断定しない。** ツールが示した判定理由 (低下不足・上昇・プラトー) を書き、
  物理的原因は切り分けの根拠があるときだけ別欄に書く。無ければ「原因未特定」。

## 2. 主張ごとに根拠を紐づける

- **図表には**リポジトリ相対の run パス、出力ファイル名、step (または平均区間) を付す。
  run 名だけでは case 間で一意にならない。
- **図には通し番号を付ける** (`Figure 1`, `Figure 2`, …)。本文から図を指すときは番号で指す
  (「上の図」は編集で位置が変わると壊れる)。番号はページ内の出現順。
- 「収束した」「一致した」と書く応答・ページには判定ツールの VERDICT を貼る (AGENTS.md)。
- **外部レビュー (codex) の指摘は、鵜呑みにせず AGENTS.md に従って検証してから採否を決める。**
  検証の結果、既に報告した主張が誤りと確認できたら、**訂正内容・根拠・影響範囲・レビュー記録への
  リンク**を残す (消さない)。未公開の草稿まで撤回履歴にする必要はない。
- 推測を断定で書かない。**特定できたことと、できなかったことを分けて書く節**を持つ。

## 3. 図の作法

- 実測・参照解と計算は凡例で明確に区別する。比較対象が無いなら原因を断定しない。
- 対数軸は明示。正規化した量は**何で割ったか**をキャプションに書く。
- 画像は埋め込み、**原寸へのリンクか動作確認済みの拡大**を付ける (`class` を付けただけでは拡大しない)。
- 日本語ラベルを使うなら実在するフォントを `matplotlib.font_manager.fontManager.addfont(...)` で
  登録してから `font.family` に設定する (この環境では `/home/sano/.fonts/NotoSansCJKjp-Regular.otf`)。
  **字化けした図をそのまま出さない。**

## 4. 仕上げのチェック

1. 条件節が**あらゆる数値結果より前**にあるか。領域図はその run の `mesh.h5` から描いたか。
2. 課した境界条件の分布はグラフにしたか。
3. ゲートの表に未実行・判定不能・FAIL の行も残っているか。制約欄を埋めたか。
4. すべての図に通し番号と run パス・出力ファイル・step があるか。
5. 訂正・撤回は根拠とレビュー記録へのリンク付きで残っているか。
6. 成果物へのリンク (README の run 一覧、plan) を示したか。README と plan の同期そのものは
   AGENTS.md の規則に従う。
