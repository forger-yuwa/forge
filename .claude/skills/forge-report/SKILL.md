# /forge-report — 計算結果を報告にまとめる

目的: 読者が**数字を信じてよいかを自分で判断できる**報告を作る。そのために必要なのは
綺麗な図ではなく、(1) 何をどう解いたか、(2) 判定ツールが何と言ったか、(3) どの run の
どのファイルか、の 3 つが**主張より先に**出ていることである。

AGENTS.md の「計算結果ディレクトリの明示」「NaN/発散チェック」「収束確認」「準定常確認」
「壁解像確認」は報告にもそのまま効く。本 skill はそれを**報告物の構成**に落としたもの。

## 0. 出力先を決める

| 読者・用途 | 出力先 |
| --- | --- |
| ユーザに見せる・図が主役 | **Artifact ページ** (`Artifact` ツールで publish)。図は PNG リンクでなくページに埋める |
| どの run が何かの恒久記録 | `case/<case>/README.md` の「## 計算 run 一覧」表 (**必須・省略不可**) |
| 設計判断・検証の結論 | 対応する `plans/active|accepted/<plan>.md` の変更ログと §6 |

Artifact は**スナップショット**であり正本ではない。ページの末尾に
「run 索引は README が正本、本ページは YYYY-MM-DD 時点」と書く。

## 1. 条件節を「最初の図の前」に置く

**冒頭固定ではない。** 要旨・結論が先にあってよい。守るのは
**読者が最初の結果図に出会う前に条件節を通過していること**だけ。典型は

> タイトル → 1 段落の要旨/結論 → **01 解析条件** → 02 以降の結果

**ただし、冒頭の要旨に置いてよいのは「良い数字」だけではない。**
冒頭で結論を述べるなら、**同じ段落の中でその結論の最大の限界も述べる**
(合わない領域・未収束・FAIL したゲートのうち最も重いもの)。
限界を後ろの節に送って冒頭を良い数字だけで埋めたら、それは
「良い数字を先に出す報告」であり、条件節が後ろにあるのと同じ違反である
(この形の失敗を実際に繰り返している。ユーザ指摘「なんかぜんぜん合ってない
ように見える」2026-09-20)。**書けないなら冒頭に結論を置かない。**

条件節に入れるもの (この 4 点セットで 1 節):

### (a) 解析領域の図

**文章で「2D 周期 1 ピッチ」と書くだけにしない。図にする。** 最低限:

- メッシュを薄いグレーで下敷きにする (解像度が伝わる)
- **境界パッチを `physID` ごとに色分けして凡例に条件の種類を書く**
  (例: `inlet (physID 1) Pt, Tt, 軸方向`)
- 主流方向の矢印、座標軸のラベルと単位
- 対象物が領域に対して小さいときは**拡大インセット**を付ける

データは run の `mesh.h5` から直接引く (`MESH/COORD` と `BCONDS/<physID>/vizBfaceNodes`)。
幾何ファイルや記憶から描かない — **図は実際に計算した領域でなければ意味がない**。

日本語ラベルは `matplotlib.font_manager.fontManager.addfont('/home/sano/.fonts/NotoSansCJKjp-Regular.otf')`
してから `font.family` に設定する (`.ttc` 指定は失敗する)。

### (b) 境界条件の表

`bcondConfig.yaml` から**実際の値を読んで**作る。記憶で書かない。列は
`境界 / 課した条件 (kind) / 値`。複数ケースを並べるなら列で対比させる。
壁温のように分布を課している場合は「実測分布」「一様 566 K」など**何を課したか**を書く。

### (c) 数値設定の表

`solverConfig.yaml` から読む。離散化 (node/cell・次数・リミッタ)、対流スキーム、
時間積分 (定常/非定常・陰解法・CFL)、乱流モデルと壁処理、気体モデル、
節点数・壁節点数・第一セル厚。

### (d) ゲートの VERDICT

**「合格したものだけ」を書かない。** FAIL や NOT CONVERGED こそ条件節に要る。

| ツール | 書くこと |
| --- | --- |
| `check_convergence.py` | VERDICT と、**どの区間で判定したか** (段階起動なら段名でなく `--segment` が連結した区間)。未収束ならその理由 (物理的に非定常なのか停滞なのか) |
| `check_quasisteady.py` | 報告する派生量が `STEADY` か。`DRIFTING` なら末尾ドリフト率 |
| `check_wall_resolution.py` | 壁ありなら常に。$y_1^+$ 平均と**目標超過の面積割合** |
| `check_mesh_quality.py` | メッシュを新造したなら AR・スキュー |

FAIL があるまま結果を出してよい。ただし**その FAIL が結論をどこまで制約するか**を
1 行添える (例:「y⁺ が 1 を超える面積が 66 % あるので、低 Re SST の壁解像は目標内でない」)。

**未判定を合格として扱わない。** ツールが `判定不能` / `NOT APPLICABLE` /
`only N usable snapshots` を返したとき、それは PASS ではない。
表には**その文字列をそのまま書き**、なぜ判定できなかったか (列が無い / スナップショットが足りない /
壁解像 run なので `utau` が出ない 等) と、**その量について何も保証されていないこと**を書く。
ゲートを回していない項目は「未実施」と書く。空欄にしない。

## 2. 主張ごとに根拠を紐づける

- **数値には run パスを添える**。図のキャプションに `run_NNNN_slug` を入れる。
  複数 run を比べた図は run ごとに凡例で区別する。
- **「収束した」「一致した」と書く応答・ページには `check_convergence.py` の VERDICT を貼る**
  (AGENTS.md)。派生量なら `check_quasisteady.py` の VERDICT。
- **外部レビュー (codex) で否定された主張はページから消さずに撤回として残す**。
  「こう考えていたが、こう反証された」は読者にとって結論と同じだけ価値がある。
  記録は `notes/reviews/<日付>-<主題>.md`、ページからはその判定を引く。
- 推測を断定で書かない。原因未特定なら「未特定」と書く。
  *特定できたことと、できなかったことを分けて書く節*を持つ。

## 3. 図の作法

- 実測・参照解は**点**、計算は**線**。同一メッシュの別ソルバは色で分ける。
- 両対数・片対数の軸は明示。正規化した量は**何で割ったか**をキャプションに書く。
- 振動・ギザギザを議論する図は、**同じ図に比較対象 (別ソルバ / 別解像度)** を入れる。
- クリックで原寸拡大できるようにする (Artifact ページでは `<img class="shot">` + 拡大)。

## 4. 仕上げのチェック

報告を出す前に、自分で次を確認する。

1. 条件節が最初の結果図より前にあるか。領域図はその run の `mesh.h5` から描いたか。
2. すべてのゲート VERDICT を書いたか (FAIL を落としていないか)。
3. すべての図・表に run パスがあるか。
4. `case/<case>/README.md` の run 一覧表を同期したか。**破棄した run も行を残したか**。
5. 撤回した主張があるなら、撤回としてページに残っているか。
6. plan に反映すべき方針・残作業が出たなら、**その応答の中で** plan §5.1 に書いたか。
