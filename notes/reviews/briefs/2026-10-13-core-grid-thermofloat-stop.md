## 1. 前提 (観測事実)

- Gref (75.5 万節点) の B0 (ライン陰解法・方向別 dt 上限 50・ITJ 5・cfl 4・緩和 0.7) は停滞し、point の止まった値 (`run_0614`、通算 20 万 step で自己変化の資格) と θ_r[65,75] で +0.63 %・Q_w で +0.51 % 違う所に止まる (§4.31・§4.33)。上限 1 にすると 2 万 step で θ_r の差が +0.65 → +0.29 % と point の値の向きに動く (§4.33)。
- B0 は微小な差を 1 step あたり約 0.4 % で増幅し、同じ入力から回した 2 本 (GPU の加算順の丸めだけが種) の差も 1e−7 の摂動と同じ速さで育つ (§4.77、Grefc、3000 step)。
- §4.95: 既定の `thermoFloat: 1` は同じ状態でも T・P・音速に相対 1e−8〜1e−7 のなめらかでない誤差を乗せ、微小な補正への残差の応答を比例させない。同じ状態 Q0 での残差の差 (`thermoFloat` 1 対 0) は縮流部で ‖ΔR‖/‖R‖ = 0.8 % (Q0 は停滞の場で ‖R‖ は大きい)、補正の向きで見て状態の相対 1e−6 程度にあたる (見積もり)。温度の反復は前の step の T から始めるので、cp などは履歴に依存する。
- 両方の経路は float と FP64 のビルドで共通 (float の演算を明示的に使う)。
- 速さ: Gref の B0 は 1 本だけなら約 23 step/s (FP64、AWS A)、2〜4 本同時で遅くなる。`thermoFloat: 0` の速さは未測定 (double の Newton を毎回回すので遅くなる見込み)。
- 利用できるバイナリ: `~/forge-fgeom7-fp64-lmp2dg` (sha 4e6e6c14、node の前処理の境界修正と診断のスイッチ入り、既定では B0 に影響しない) と `~/forge-fgeom7-fp64` (7e95e5bb、B0 の既存 run のバイナリ)。

## 2. 私の案 (縛られなくてよい)

- 腕: Gref の `run_0608` res_60000 (B0 の停滞の場) から、B0 のまま `thermoFloat` 1 (T1) と 0 (T0) を同じバイナリで各 2 万 step (または 6 万 step)。可能なら T0 の複製 (同じ入力) を 1 本足して、実行間差の大きさも見る。
- 見る量: θ_r[65,75]・θ_r[84,94]・Q_w の窓平均の T0 − T1 と、point の止まった値からの差。縮流部の残差。
- 読み方の案: T0 の θ_r が point の止まった値の向きに 0.1 % 以上動く → 熱物性の経路が B0 の止まる先に効いている。T0 − T1 が実行間差の大きさ以内 → 効いていない。
