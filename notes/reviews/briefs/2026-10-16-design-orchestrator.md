## 設計 (plan §4 の要点)

1. 3 つの層を分ける。
   - 要求カード (データ)
   - 機種ごとのレシピ (データ、版つき)。段の並び・既定の設定・判定のプリセット・失敗の返り値ごとの選べる手・終える条件。
   - 段の部品 (契約つきの関数) と、決定的な状態機械の実行役 (台帳で再開)。
2. 失敗の返り値はレシピで選べる手の一覧に対応づける。
   - 手が 1 つに決まれば実行役が選ぶ。
   - 2 つ以上が残る・想定外の失敗のときだけ、判断役に形の決まった問いを出す。
3. 判断役とのやりとり:
   - 判断役の答えは、一覧から 1 つ・理由・確信の度合い。台本や閾値の変更はさせない。
   - 実行役は答えを機械的に検査する。形式・一覧・手の前提・確信の度合いを見て、通らなければ人に返す。
   - 判断役は設定ファイルで切り替える: `fable` / `codex` / `claude` / `local` (OpenAI 互換の API)。
   - 過去の止まり方を問いの組にして、判断役ごとの成績を出す。ローカル LLM に任せる範囲の線引きはこの成績で決める (決めるのはユーザ)。
4. 入口と台帳:
   - 入口は CLI `forge-design run <card>`。skill は薄くする (カードを作る・回す・報告する)。
   - AGENTS.md に「設計の run は `forge-design` 経由」と書く。
   - 台帳は run の外の 1 つの JSON。sha256 で照合して再開する。
5. 範囲: 最初は風洞ノズル 1 機種。
   - case/71 の台本を段の部品に置き換えて、同じ結果を確かめる。
   - 格子の段を一般化する。
   - 判断役の口と試験の組を作る。
   - Haiku・ローカル LLM で再現する。
   - ベル・デュアルベル・SERN は後で、各セッションの成果をレシピと段に載せる。

## 問い

1. この方向 (決定的な実行役 + データのレシピ + 止まったときだけ形の決まった問い) は、ユーザの要求に対して妥当か。代わりの形があれば、その利点と欠点。
2. 判断役の口の設計 (一覧からの選択・検査・人に返す) の穴。特に:
   - (a) 一覧に無い失敗を、どう問いにするか。「人に返す」しか無くなるのでは。
   - (b) 確信の度合いを自己申告させる意味。
   - (c) ローカル LLM のような弱いモデルで、問いの組の成績をどう測り、どこまで任せるか。
   - (d) 判断役が根拠のファイルを読めない場合 (ローカル LLM に読ませる範囲)。
3. 最初の範囲の切り方と、§6 V1〜V4 の検証の穴。特に:
   - 格子の段の一般化が最大の難所と見ている。手組みの格子を一般化する前に、雛形の格子で済む機種を先にすべきか。
   - V1 の「同じ結果」の許容の決め方。
4. 既存の部品・別のセッションの plan との関係で注意すべきこと。
   - `forge-gate` の推奨設定の正本と起動前の関門。
   - 推力ノズル・SERN の各セッション。
   - 調整板の運用。
5. やらない方がよいこと。
