# 諮問: ホストメモリ削減 R1–R3 — 統計でなく「GPU への入力経路の一致」で決着させる試験は成立するか (2026-10-07)

関連 plan: `plans/active/architecture-solver-host-memory.md` §6.2・§6.3 (固定幅 A/B は判定不能、限定 `done` も却下)。前回: `notes/reviews/2026-10-07-hostmem-fixedwidth-undecidable-diagnose.md`。
エスカレーション条件 4 (承認済みの手順に無い試験へ進む前) と 1 (§6 の検証計画の変更)。

## 主張 (呼び出し側、検証したい)
R1–R3 (commit 93e55957、base 9c9f623c) は**ホスト側の確保範囲・初期化の順序・ホスト参照の検査**だけを変え、カーネル・起動設定・デバイス側の確保 (`c_d` 全変数を `nCells_all`、`p_d` を `nPlanes`) は変えていない。
したがって GPU の計算に影響しうる経路は (1) H2D の中身、(2) デバイス確保の名前・大きさ・順序 (アドレスや未初期化領域の内容に効きうる)、(3) カーネル起動の順序・回数、に限られる。
(1)(2)(3) が両ビルドで同一なら、両ビルドの GPU は同じ入力から同じ操作列を実行し、出力の差は GPU の非決定性 (atomicAdd の加算順序等) だけになり、その大きさは base 同士の再実行で特徴づけられる。

## 提案する試験 (事前登録の案)
- 両コミットに同じ env 診断 (例 `FORGE_TRACE_DEVICE_IO=1`) を載せた 2 バイナリを作る (診断のコードは同一、既定は無効で挙動不変)。記録: (1) 全 H2D (`cudaMemcpy` HostToDevice、wrapper 経由と直接呼び出しの両方) の (呼び出し箇所・変数名が分かれば名前・バイト数・内容の 64bit ハッシュ)、(2) 全 `cudaMalloc`/`cudaFree` の (箇所・名前・バイト数) の順序列、(3) カーネル起動の (名前・grid/block) の列 — (3) は重いので初期化と 1〜2 step だけ。
- 全 30 構成 (case/66 の構成表) で、base 2 本・new 2 本。判定: (2)(3) は 4 本で列が完全一致。(1) は base 同士で一致する H2D (= 決定的な入力: ファイル・設定・格子由来) について base 対 new で完全一致。base 同士で内容が変わる H2D (= デバイス由来の D2H→H2D、非決定的) は名前・バイト数・順序の一致だけを見る。
- 一致すれば: 「R1–R3 は GPU への決定的な入力・確保・起動の列を変えない」。§6.2/§6.3 の差は GPU の非決定性で説明され、変更起因ではない、と結論する。一致しなければ: 不一致の H2D/確保の名前から原因を追う。

## 問い
1. この経路の列挙 (H2D・確保・起動) は十分か。他に GPU の結果に効く経路はあるか (例: ストリーム・同期・ホストのページロック・`cudaMemset` の有無、`cudaMemcpyToSymbol`、テクスチャ、未初期化デバイス領域を読むカーネル、ホストのタイミング依存、乱数の種、環境)。
2. 一致したとき、上の結論は言えるか。言えないなら何が足りないか (限定事項として書く範囲)。
3. 事前登録すべき合格条件の文面 (D2H 由来の H2D の扱いを含む)。トレースを入れる場所の漏れ (直接の `cudaMemcpy` 呼び出しが多い) をどう防ぐか (例: `cudaMemcpy` をラップするのでなく CUDA のプロファイラ API / `CUPTI` の callback で全部取る、`nsys` のトレースを使う)。
4. これで決着できるなら、用途に基づく許容差を定義しなくても `done` にできるか。
