### 2. 改訂案 (調査ファイル §3 の要約。ユーザが「おｋ」で方向を承認)

- 3 つの原則: (1) 守りは出口 (判定) に置き、途中は AI に任せる。(2) 仕組みは同じことを繰り返すようになってから作る。
  (3) 決まりを足すときは文章でなくプログラムの検査にし、置き換わる文章の決まりを消す。
- 役割: ユーザ = 依頼の原文・要求の解釈の確認 (ユーザが決める欄)・予算の承認・新しい手順を正式な道具にするかの判断。
  AI = カードを作る・道具を選んで回す・失敗したら原因を調べて直す / 別の手 (台本を書いてよい)・判定の出力つきで報告。
  プログラム = 合否の判定・予算の計数と停止・既存の run と成果物を上書きしない・記録を自動で残す。
- **AI が変えてはいけない 4 つ**: (1) 判定器と公差 (`wt_qualify`・`check_*` とその閾値)、(2) ユーザが決めた欄 (公差・壁温・寸法・成果物の選択)、
  (3) 予算 (GPU 時間・ディスク)、(4) 既存の run と成果物。これ以外 (数値設定の調整・台本・格子の作り直し・手順の並べ替え) は直してよく、直したことは報告に書く。
- 知識の少ないモデル (ローカル LLM など) には直す権限を持たせない (今の手順書 `procedures/design-chain-quickstart.md` の「自分で直さない」(16 行目))。
- 実行役は薄くする: 既知の機種の流れをコードにしたものにとどめ、各段の判定で進むか止まるかを決め、止まったら理由 (どの判定がどの値で落ちたか・関係するファイル) を
  1 つのファイルに書いて終わる。判断役の専用の仕組み (digest・引用の照合・問いの組) は知識の少ないモデルに判断させる要求が出るまで作らない。
  そのときも選べる手を「もう一度 (一過性のときだけ)」と「人に返す」に絞る制限 1 つから。再開と台帳 (§4.5) は残す。
- 道具の説明は各道具の `--help` と冒頭に書く (目録の専用ファイルは作らない)。索引は `design/CAPABILITIES.md`。
- 新しい要求: 既知の機種で条件だけ違う → 実行役 (実績の範囲かは実績が数件たまるまでユーザに確認)。新しい機種・道具の新しい組み合わせ → AI が探索として台本を書いて試す
  (case の下の探索用のディレクトリ、合否は既存の判定器)。同じ台本を 2〜3 回使ったら今の開発フロー (plan・レビュー) で道具にする。
- 記録: 新しい台帳の形式は作らない。足すのは依頼の原文と AI の報告 (何を試し、何を直し、どの判定で通ったか) だけ。最後は人が報告を読む
  (判定器は数値の不合格を捕まえるが、もっともらしい誤った説明は捕まえない)。
- 確かめ方: 答えの分かっている依頼を数件 (正常なもの・止まるべきもの) 用意して AI に回させ、成果物まで届いたか・誤って合格させなかったか・人に返すべき所で返したか を見る。
  最初は軽い範囲 (カード → 問題 YAML → 格子)、GPU の段は後から。
- 今は作らない: ツールごとの専門家の AI、検証済みの範囲の一覧、目録の専用ファイル、判断役の digest・引用の照合・問いの組、MCP のサーバ、新しい台帳の形式、探索から recipe への専用の審査。
- plan との差分 (調査ファイル §3.10): §4.1〜§4.3・§4.5・§4.7 はそのまま。§4.4 は止まった理由のファイルだけに。§4.8 skill の中身は 4 つと道具の索引だけ。
  §6 V3 は依頼の課題集で通しの成績。「自分で直さない」は知識の少ないモデルだけに。

### 3. ユーザ決定 (2026-10-17、plan §4 の冒頭に記録済み)

- 方向: 上の改訂案でよい (「おｋ」)。ローカル LLM について「出口の判定で守る、というのがちゃんとわかんない」と質問があり、
  「知識の少ないモデルは決まった流れを回すだけで直さない、賢い AI が直す」と説明して了承された。LLM が流れ (台本) を組む形は残る。
- 予算: 一律の上限は置かない。「ケースバイケース」(パレート解を取るとき・メニューしだいで大きく変わる)。依頼ごとに AI が見積もり
  (`design-intake` の「コスト見積もりと承認」: メニューと本数 × その PC で測った 1 本の時間)、ユーザが承認した値をその依頼の予算とする。
- 依頼の原文の置き場所: 設計を行うリポジトリの case のディレクトリ (公開のリポジトリには載せてよい情報しか載せない運用。plan §4.7)。

## 主セッションの追加案 (まだ plan に書いていない)

- A1 **4 つのうち (1) をプログラムで守る**: qualification の記録に判定器のファイル (`wt_qualify.py`・`check_*.py`・`settle_presets.py` など) の sha256 を書き、
  main (または固定した版の一覧) と違えば判定を拒む。または判定を main の固定 commit の別 checkout で回す。
- A2 **(3) 予算をプログラムで守る**: `run_case.sh` (forge の唯一の入口) が依頼ごとの予算の台帳 (カードの承認済みの値) に使った GPU 時間を足し、超えたら起動を拒む。
- A3 **(2) ユーザが決めた欄をプログラムで守る**: qualification が solverConfig・境界条件の物理の値 (入口の Pt・Tt・組成、壁温、ガス) をカードと照合する。
  数値の設定 (CFL・リミッタ・段階起動) は照合しない (AI が直してよい範囲)。
- A4 **(4) 既存の run と成果物**: accepted になった run と成果物のディレクトリを読み取り専用にする (chmod)。
- A5 §4.4 は「止まった理由のファイル」(§4.3 の返り値の和 + 関係するファイルのパスと sha256) にし、digest・引用の照合・問いの組・`local` の backend を §5.1 から外す
  (将来の項目として「必要が測れたら」の条件つきで残す)。
- A6 §6 V3 を「依頼の課題集」に置き換える: 正常 3 件 (既知の機種で条件違い)・止まるべき 3 件 (公差が届かない依頼・ユーザ欄が欠けた依頼・予算が足りない依頼) を事前登録し、
  強い AI と知識の少ないモデルで回して、到達・誤合格 0・人に返すべき所で返したか を数える。最初は GPU なし (カード → YAML → 格子)。

## 仮説

- 出口の判定で守る形は、判定器が測っている量については強いが、**測っていない量** (物理の設定・格子の対象の形状・判定器そのもの・予算) では守りにならない。
  そこを A1〜A4 のプログラムの検査で埋めれば、文章の決まりを増やさずに 4 つを守れる。
- 新しい機種・新しい解析領域では**判定器そのものが無い**ことがある。そのとき「出口の判定」は空で、AI が合格を自分で宣言できてしまう。

## 問い

1. 改訂案の「途中は AI に任せ、出口の判定で守る」で、forge の設計の流れに**穴**はあるか。特に、今の判定器が測っていないもの (§4 の観測) のうち、
   出口で塞ぐべきものと、塞がなくてよいもの (報告を人が読むことで足りるもの) の線引き。
2. 新しい機種・新しい解析領域 (判定器が無い) の探索で、AI が合否を自分で決めない仕組みは何が最小か
   (例: 判定の基準を事前に書いてユーザが承認する = ユーザが決めた欄に入れる)。
3. A1〜A4 は妥当か。過剰なもの、足りないもの、より単純な代わり (例: A1 を「別 checkout で回す」にするか sha の照合にするか)。
4. AGENTS.md のエスカレーション条件 4 (手順に無い修正の前に上位に諮る) と、改訂案の「途中は AI が直してよい」はぶつかる。設計の依頼の中での途中の修正に条件 4 を
   適用しない、という書き分けでよいか。ほかに直す必要のある AGENTS.md・手順書の決まりはあるか。
5. §4.4 を A5 のように軽くしてよいか。§4.3 の手の一覧は残す (知識の少ないモデルに選ばせるとき用) でよいか。
6. §6 V3 の置き換え (A6) の事前登録で足りないものは何か (件数・止まるべき依頼の種類・誤合格の数え方)。
7. §5.1 の優先順 (今: 親 plan の契約 → forge-gate 統合 → idle 停止 → 失敗の分類 → 実行器 → 格子の段 → 判断役 → カード・CLI) をどう変えるべきか。
   ユーザの懸念 (ルールが増えすぎ・ややこしさ) から見て、前の案で残すべきでないものはあるか。
