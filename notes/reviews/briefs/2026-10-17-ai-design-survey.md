# 調査依頼: AI による自律的な設計 (エンジニアリング設計・シミュレーションの自動化) の最新動向 (2026-10-17)

- 依頼者: 主セッション `AI設計の調査` (作業ツリー `forge-aisurvey` / `feature/ai-design-survey`)
- 依頼先: codex (`gpt-6-astra`、`model_reasoning_effort=high`、`-c web_search=live` で Web 検索を有効にして回す)
- 種類: 技術調査 (エスカレーション条件の諮問ではない)。結果は `notes/investigations/2026-10-17-ai-design-survey.md` に主セッションがまとめる
- 分担: 同じ依頼を 3 本の codex に分けて並行で回す。各 codex には起動時に「担当: パート 1」などと伝える (§4)

## 1. 目的

forge (公開リポジトリ。圧縮性 CFD ソルバと、ノズル設計の道具 `design/forge_design`) の設計の流れを、
「AI がユーザのニーズから道具を選び、工程を組み、回し、うまくいったものをプログラムとメニューに固めて残す」形に発展させたい。
その設計の材料として、2024〜2026 年の研究と製品の事実を**一次の出典で**集めてほしい。

## 2. forge の今の状態 (背景)

### 2.1 今の設計の流れ

- 要求カード (YAML) → 問題 YAML → 格子 → Euler → NS (停止規則 v2) → 境界層の較正 → 判定 (`wt_qualify`) → 成果物 (STEP・格子・Fluent・Excel・報告)。
- 各段は決定的なプログラムで、段ごとに「成功の印」と「止まったら人に見せるもの」がある。判定 `wt_qualify` は終了コードで次の手 (成果物を作る / 較正し直す / 人に返す) を返す。
- 手順書 `procedures/design-chain-quickstart.md` を AI が 1 コマンドずつ打って回せることを確かめた (2026-10-16)。
- 次に作るもの: オーケストレータ (`plans/active/tooling-design-orchestrator.md`)。
  - 工程を順に回す実行役は普通のプログラム。
  - 止まって 2 つ以上の手が残るときだけ、判断役の AI (Fable / codex / ローカル LLM) を呼ぶ。答えは手の一覧から 1 つ + 判定の要約からの引用で縛り、実行器が検査する。
- 今のモデル分担 (`AGENTS.md`「モデル分担とエスカレーション」): 上位 (判断) / 中位 (実装・主セッション) / 下位 (run の機械的作業)。分担の軸は「誤りをツールで判定できるか」。

### 2.2 ユーザが最終的に想定している姿

- ツール群 (forge・NASA CEA・熱評価・gmsh・凝縮モデル・その他の道具など) の中から、AI がユーザのニーズに基づいて設計の工程を組む。
- 必要ならツールごとに担当の AI (専門家) を置き、互いにやり取りさせる。
- 新しい要求 (例: 計算したことの無い機種・条件) では AI が自由に動いて試し、うまくいったものをプログラムとメニューに固めて残す。
- ユーザの元の依頼の文章とやり取りは正本として残し、計算への入力 (YAML) はその時点の解釈として扱う。

### 2.3 主セッションのたたき台 (調査で検証・修正してほしい)

1. ツールの目録 (各部品の説明書: 何をする・入出力と単位・検証済みの範囲・成功の判定・所要時間)
2. 計画役の AI: ニーズ + 目録 → 工程を提案 → ユーザが了承
3. 実行役 (プログラム): 工程を順に回し、各部品の判定で進む・止まる
4. 判断役の AI: 止まったときに選択肢から選ぶ
5. 専門家の AI (skill・サブエージェント): 知識の重いツールから置く
6. AI どうしのやり取りは決まった形 (問い・答え・判定の記録) を通し、全部記録する

## 3. 調べてほしいこと

### (a) LLM エージェントで CFD・CAE・CAD・設計の工程を自動化した研究と製品 (2024〜2026)

- OpenFOAM を LLM で動かす研究 (MetaOpenFOAM・OpenFOAMGPT・Foam-Agent など。似た名前の別研究に注意)。ほかの CFD・FEA ソルバ (SU2・Fluent・Abaqus・FEniCS など) の例。
- 格子生成・後処理・パラメトリックな設計探索・最適化に LLM を使った例。
- CAD の生成 (テキスト・画像からの CAD コード生成、CAD のエージェント)。
- 商用の CAE・CAD の AI 支援 (Ansys・Siemens・Dassault・Autodesk・COMSOL・Altair・nTop など。物理の代理モデルの製品と、LLM の対話・自動化の製品を区別する)。
- ロケット・推進・空力の設計への適用があれば優先して拾う。

### (b) 似た分野の自律化の設計の型

- 化学・材料・生物の自律研究 (Coscientist・ChemCrow・A-Lab・The AI Scientist・AI co-scientist・Virtual Lab など)。
- 「計画 → 実行 → 検証 → 振り返り」の回し方、人の了承の挟み方、実験 (計算) の予算の扱い。

### (c) 道具を組む仕組み

- 道具の目録・登録と接続の約束事 (MCP、関数呼び出しのスキーマ、A2A など)。道具の説明に何を書いているか (入出力・前提・副作用・費用)。
- 計画役 + 実行役 (plan-and-execute、ReWOO、LLMCompiler など)、決定的なワークフローと自律エージェントの使い分け。
- マルチエージェントの枠組み (LangGraph・AutoGen・CrewAI・OpenAI Agents SDK・Claude Agent SDK など) の、状態の持ち方・記録・再開・人の了承 (human-in-the-loop) の機能。
- 試行でうまくいった手順をプログラム・道具として固めて再利用する仕組み (skill の蓄積、道具の自動生成 など)。

### (d) 検証と信頼性

- AI が組んだ計算をどう検証しているか: 上記の研究が何を成功の基準にしたか (成功率・基準解との比較・人の評価)、V&V (ASME V&V 10/20、NASA-STD-7009 など) との関係。
- 合格の条件の事前登録、結果の由来 (provenance) の記録 (W3C PROV・RO-Crate・AiiDA などの例)。
- 失敗の例: もっともらしい誤り、暴走 (自分の制限を書き換える・破壊的な操作)、費用の膨張、評価の甘さ。実際に報告された事例を出典つきで。

### (e) 単体の AI + 道具か、専門家の AI を複数置くか

- 比較した実例 (同じ課題で単体と複数を比べた研究、製品開発の報告)。
- それぞれが向く条件 (課題の分解しやすさ・文脈の長さ・費用・失敗の伝播)。マルチエージェントの失敗の分類の研究があれば。

## 5. 出典の規則 (厳守)

- **知っている事例でも、必ず Web で一次の出典を開いて確かめてから書く**。学習データの記憶だけで書かない。
- 一次の出典: 論文 (arXiv・査読誌・会議録)、公式の製品ページ・公式ドキュメント・公式の発表、公式の GitHub リポジトリ。
  ニュース・ブログのまとめは二次の出典。使うときは「二次」と明記する。
- 各事例に付ける項目: 名前 / 主体 (組織) / 初出の年月 / URL (一次) / 何を自動化したか / 構成 (単体か複数か、道具の繋ぎ方: 関数呼び出し・MCP・コード生成・RAG など) /
  検証の仕方 (何を基準に成功と言ったか) / 成熟度 (研究の試作・OSS・商用の一般提供・ベータ) / 報告された失敗・限界。
- 論文は著者 (筆頭)・年・arXiv ID か DOI を付ける。製品は発表の日付と公式ページを付ける。
- 確かめられなかったものは消さずに「未確認 (理由)」と書く。推測は文頭に「推測:」と書いて事実と分ける。
- 宣伝の文句 (「何倍速い」「完全自律」など) は「主体の主張」と明記し、独立の検証があれば併記する。無ければ「独立の検証なし」と書く。
- 名前の取り違えに注意する (同名・似た名前の別研究、版の違い)。

## 6. 出力の形

日本語。固有名詞・識別子・論文名は原語。Markdown で次の順に書く。

1. 事例の表 (列は §5 の項目)。
2. 見えた設計の型: 型ごとに、中身・利点・欠点・その型を使った事例 (表の行への参照)。
3. forge への示唆: §2.3 のたたき台 ①〜⑥ と照らして、裏付けのあるもの・修正すべきもの・足りないもの。
   **推奨は 1 つに絞り**、根拠は表の行 (出典) か §2.4 のファイルの `ファイル:行` で示す。
4. 確かめられなかったこと・出典の弱いもの。
5. (あれば) 他パート向けの出典。
